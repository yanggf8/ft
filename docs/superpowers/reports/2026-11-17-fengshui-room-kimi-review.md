• ## Findings

**K01 — Blocking｜證據徽章把不同維度混成一維，部分初值會誤導。**  
位置：spec §2「證據徽章」與徽章初值表；研究報告 §2。

`supported / mixed / indirect / untested` 同時混用「結果一致性、研究直接性、效果量」，無法忠實表示研究現狀：

- `bed_corner / seat_corner` 標 `mixed`，會讓人以為「尖角對人」本身被直接測過且結果不一致；實際主要是抽象圖形曲線偏好，真實家具證據薄弱且近期未複製。至少應是「**間接研究・結果不一致**」。
- `bed_clutter / seat_clutter` 標「只有間接研究」也不精確；Saxbe & Repetti 是直接的相關研究，只是不能推論整理會造成改善。
- `bed_back` 的 `indirect` 隱去了底層 prospect-refuge 研究本身不一致。
- `bed_door_view` 同時包含「看不看得到門」與「床尾正對門」；後者在研究報告 F04 是無直接研究，不應共用一個不加說明的徽章。
- `bed_light / seat_light` 的「效果小到中」必須指明是對睡眠、情緒、注意力還是晝夜節律，不能讓使用者自動套到「專心」或整條風水主張。

**修正建議：**徽章至少保留「直接性＋結果狀態」兩軸，例如「間接研究・結果不一致」「相關研究・不能推論因果」「無直接研究」。效果量與研究設計放進「看研究」，不要用一個通用效果量標籤涵蓋所有結果。不同證據的主張應拆卡或拆句。

**K02 — Blocking｜即使沒有「所以、證實」，卡片視覺仍可能實質替風水背書。**  
位置：spec §0、§2、§6；研究報告 §3、§4。

目前徽章是「每張格局卡」的徽章，視覺上很容易被讀成「這條風水有研究支持」。最後才放說明卡，無法消除前面的第一印象。spec 也沒有明文化研究報告的重要限制：**PP 只能當詮釋語言，不得提升任何徽章；無直接研究時不能改用 PP 編一個合理的大腦故事。**

**修正建議：**

- 徽章只能放在「你的大腦怎麼看」欄內，標成「相關環境研究」，並固定附「這些研究不是在檢驗風水」。
- `untested` 卡不得用「大腦理論上會警戒，所以可能……」補出風水合理性。
- 開場先放一句短揭露，結果最後再放完整說明；§10 第 3 項不應二選一。
- 驗收不能只掃連接詞，還要人工看實際手機畫面，確認不會把徽章誤讀成風水認證。

**K03 — Blocking｜語料與徽章缺少「回原文核對」閘門。**  
位置：spec §2「實作時以研究報告為準」、§7 T6、§8 Batch 1；研究報告表頭。

研究報告明寫「大部分文獻只讀摘要或二手轉述，引用到產品文案前須回原文核對」。T6 只檢查文獻鍵能解析，完全不能防止錯引、效果量誤植或把相關寫成因果。

**修正建議：**Batch 1 增加逐篇原文核對清單，至少記錄研究設計、樣本、實際測量的 outcome、限制、是否全文核對。未核對的文獻不得支撐 `supported`；必要時先以保守文案上線。

**K04 — Blocking｜「對答案」仍有部分文案超過 n=1 能支持的結論。**  
位置：spec §0、§2 固定說明卡、§3.1 對答案。

「一個人一次不能證明風水有沒有用」是必要且正確的 disclaimer，但：

- 「大腦在學的就是這個差距」把 PP 寫成確定事實，也沒有測量任何學習。
- 只能觀察「這次預測與自評的差距」，不能判斷差距由調整造成，也不能由一次結果評估預測校準能力。
- 同時允許同房間最多 3 個實驗，會讓多個調整互相混入，卻仍逐項顯示「你預測、實際」的差距，更容易被解讀成單項效果。

**修正建議：**改成「可以用預測與回報的差距作為反思線索」；明寫「無法分辨調整、預期、生活變化與評分波動」。UI 宜用「自我觀察」而非強調「實驗驗證」。v1 最好每房型同時只允許 1 個進行中項目，或至少明確揭露同時調整無法分項解讀。

**K05 — Blocking｜條件式 UPDATE 沒有原子執行 30 天上限，且「進行中」未定義。**  
位置：spec §3.3、§4 回報錯誤、§5 條件式 UPDATE。

目前條件只有：

```sql
reported_at IS NULL AND created_at <= ?
```

這只能擋未滿 7 天，**不能擋超過 30 天**。即使 UPDATE 前先 SELECT 檢查，也仍存在跨過 30 天邊界的先查後寫競態。

另外，建立上限所用的「進行中」若只是 `reported_at IS NULL`，過期列會永久占用 3 個名額。

**修正建議：**固定定義：

- 進行中／可回報：`reported_at IS NULL AND created_at >= expiry_cutoff`
- 開放：`created_at <= open_cutoff`
- 滿 7 天可回報；剛好滿 30 天仍可回報；超過 30 天才過期。

單次取得 `now`，衍生 `open_cutoff = now - 7d`、`expiry_cutoff = now - 30d`，並把兩個時窗條件都放進 UPDATE：

```sql
WHERE id = ? AND user_id = ?
  AND reported_at IS NULL
  AND created_at <= :open_cutoff
  AND created_at >= :expiry_cutoff
```

affected=0 再以 `id + user_id` 回查，區分 404、太早、已回報、過期。

**K06 — Blocking｜遮蔽契約前後矛盾，而且只遮住 GET 不足以保證整個 API。**  
位置：spec §3.2、§3.3、§4、§7 T8。

- §3.3 說過期後可看預測。
- T8 卻說「未回報的 view 不含 `predicted`」，會把過期但未回報者也遮住。
- POST 建立與冪等重放可能回傳完整結果，spec 沒有規定是否也要遮蔽。
- 若共用 DB row/view serializer，很容易在其他回應漏出。

**修正建議：**定義唯一的伺服端 view 轉換：

- 未回報且未過期：省略 `predicted`。
- 已回報或已過期：可回傳。
- GET、建立回應、冪等重放全部經過同一轉換；report 必須在原子 UPDATE 成功後才回完整結果。
- `Option` 必須配合 `skip_serializing_if`，並對**實際 JSON 鍵不存在**做測試，而非只檢查 Rust 欄位是 `None`。

這能降低回報時的錨定，但不是保密邊界；使用者本來就知道自己輸入過的預測，不應宣稱能防止刻意找回。

**K07 — Blocking｜條件式 INSERT 方向正確，但完整冪等與競態協定尚未寫完，測試也驗證不到 SQL。**  
位置：spec §4 冪等、§5 條件式 INSERT、§7 T7–T9。

塔羅除了 INSERT，還在撞鍵或傳輸失敗後先回查 requestId，再決定重放或衝突，見 `crates/api/src/routes/tarot.rs:385-393`、`crates/api/src/routes/tarot.rs:421-437`。本 spec 缺少這段。

**修正建議：**

1. COUNT 與 NOT EXISTS 使用相同 `expiry_cutoff`，只計未過期的進行中列。
2. affected=0、UNIQUE 撞鍵、甚至不確定是否已寫入的傳輸錯誤後，都先回查 `(user_id, request_id)`。
3. 同語意 body 回 200 原結果；不同 body 回 `IDEMPOTENCY_CONFLICT`；否則再分類總數上限或同題進行中。
4. report 網路重試也應定義：同 actual 可回 200 完整結果，不同 actual 才回 409；否則成功回應遺失後，使用者只能得到 `ALREADY_REPORTED`。
5. 增加實際 libSQL/Turso 整合測試：4 個並發建立最多成功 3 個、同題並發最多 1 列、同 requestId 並發只留 1 列、並發 report 不覆寫、30 天邊界不能晚收。T7–T9 的 native 純函式測試無法覆蓋這些保證；DB helper 實際走獨立 HTTP statement／batch，見 `crates/api/src/services/db.rs:261-270`、`crates/api/src/services/db.rs:289-319`。

**K08 — Should｜預測題措辭與 1–5 分輸入互相矛盾，三次評分的參照期間也不一致。**  
位置：spec §3.1 第 2、3、5 步；§10 第 2 項。

「你猜會變幾分」是在問變化量，但輸入卻是 1–5 的絕對分數。基線「最近睡得好嗎」與安心感「現在覺得」又使用不同時間範圍，七天後難以用相同語意回答。

**修正建議：**

- 預測改問：「調整後的一週，你猜這題會是幾分？」允許維持或變差，不預設改善。
- 三次使用相同參照期間，例如基線「過去 7 天」、預測「調整後的 7 天」、實際「過去 7 天」。
- 補端點錨定，如 1「很不安心」、5「很安心」；睡眠與專心也各自補 1／5 錨點。
- 回報實際分數時，最好連 baseline 也先不顯示，送出後再一起揭曉，進一步減少錨定。
- 加一個固定選項確認「是否實際做了調整」，不必因此收自由文字。

1–5 分適合低負擔自我觀察，但不要包裝成經驗證量表。

**K09 — Should｜存版本號卻不存語料快照，改版後舊實驗可能無法正確重顯。**  
位置：spec §4、§5 `ruleset_version / corpus_version`、§6 lab。

只存 `itemId / adjustmentId` 與版本，若舊版語料沒有永久保留，lab 無法知道使用者當初選的是哪段調整；單純存 `"1"` 不能重建內容。徽章或文獻改動是否 bump corpus 也未定義。

**修正建議：**比照塔羅保存成品快照的做法（`crates/api/src/routes/tarot.rs:415-426`），至少存建立時的題目與調整文字快照；或明確保留所有歷史版本並依版本解析。規定任何使用者可見的卡片、徽章、文獻語意改變都要 bump 對應版本。

**K10 — Should｜API wire 契約還缺幾個會直接影響前端的欄位與錯誤規則。**  
位置：spec §4、§10 第 4 項。

需要補齊：

- `requestId` UUID 形狀驗證；塔羅先例在 `crates/schema/src/tarot/mod.rs:246-257`。
- report／delete 的無效 id、他人與不存在資料的 400／404 規則。
- 列表與單筆 view 的完整形狀，包括 `status、opensAt、expiresAt、baseline、actual、createdAt、reportedAt`；狀態由伺服端以同一個 now 衍生。
- `items + nextCursor` 分頁形狀，沿用 `page_query` 的 1–20 限制與 `(created_at,id)` cursor，見 `crates/api/src/routes/common.rs:408-455`。
- 總數已滿與同題重複最好有不同錯誤碼或 `reason`，否則前端無法給具體提示。
- DTO 放 ft-schema 共用，DB row 留在 API 內部，避免前端另寫一套。
- 「全部 no-store」應包含錯誤回應與 `Vary: Authorization`；現有通用 error helper 本身不設 cache header，見 `crates/api/src/error.rs:18-31`，不能只照抄塔羅成功回應路徑。

**K11 — Should｜禁用詞測試不足以守住恐嚇、背書與理氣紅線。**  
位置：spec §2.1。

目前清單會漏掉「漏財、運勢下滑、影響婚姻、有損健康、意外、災厄、研究印證、有科學根據、腦科學支持」等等同效果說法。理氣排除也幾乎沒有測試詞，例如「命卦、吉方、財位、文昌、桃花、流年、飛星、羅盤、五行、缺角」。

**修正建議：**擴充分段詞表與跨欄組合文案測試，並加入人工語意審稿。不要只靠 substring：研究段可能合理出現「睡眠、焦慮」等詞，重點是不得寫成風水造成的恐嚇或醫療宣稱。

**K12 — Should｜localStorage 的居家格局資料缺少足夠的隱私揭露與保存期限。**  
位置：spec §5「問答不落庫」、§6 `fengshui_room_{room}`。

不落庫與不收自由文字是好的資料最小化，但 localStorage 會無限期保留，共用裝置上的下一位使用者可能看到房間格局。

**修正建議：**在問答開始前明示「答案只保存在這個瀏覽器、不會上傳」，提供顯眼的「清除我的房間答案」，並考慮版本化 key 與合理 TTL。建立實驗時也應簡短說明會上送哪些項目與兩組自評分數。

**K13 — Should｜幾個所謂「零成本調整」其實可能花錢或有安全負擔。**  
位置：spec §2「可以試試看」。

「加屏風、遮光簾」通常需要購買，「移床」也可能需要人力或空間，不符合自己的零成本承諾。

**修正建議：**改成「不購買化煞商品的低成本調整」，優先提供關門、使用現有布簾、整理一小區、調整枕頭方向等選項；涉及大型家具時提示量力而為、不要獨自搬重物。

**K14 — Should｜目前流程仍偏問卷，結果頁資訊量也過高。**  
位置：spec §1.2、§2、§6、§7 站長驗收。

臥室連答 8 頁，接著最多 8 張、每張四段的卡，再進入四個評分輸入，核心「先猜後試」出現得太晚。七天後又沒有任何回流機制，站長很可能完成建立就忘記回報。

**修正建議：**

- 預設只展開 flag／mild；ok 收進「已符合常見建議」折疊區，unknown 收進「尚待確認」，不要形成總分或吉凶評級。
- 問答以可點選的房間俯視圖、進度與快速返回降低問卷感。
- 預測頁用「現在 3 → 一週後你猜〔4〕」的緊湊形式。
- 提供開放日 countdown、加入行事曆或本地提醒。
- 站長驗收除了走完流程，還應確認能正確說出「研究不是在證明風水、這次結果不證明調整有效」，否則流程順暢但理解錯誤仍算失敗。

---

**K15 — Nit｜「床邊兩公尺內」是沒有依據的精確門檻。**  
位置：spec §1.2 `bed_corner`。

研究報告沒有支持 2 公尺界線，現代通行說法也未在此建立此距離。這會讓問答看起來比證據更精確。改成可判讀的空間描述，或明說距離只是產品操作定義，不是研究門檻。

## 對 §10 待決項的建議

1. **7／30 天可保留**，但只是產品回訪時窗，不是「七天足以判斷效果」；邊界採滿 7 天開放、滿 30 天當下仍有效。
2. **量尺採相同 7 天參照期間、1–5 絕對分數與端點錨定**，不要問「會變幾分」卻收絕對分。
3. **說明開場短講、結果最後完整講**，不能只放最後。
4. **保留 FK cascade 與 UNIQUE(user_id, request_id)**。UNIQUE 是並發冪等的一致性是必要條件，不只是風格偏好；也符合 `scripts/schema.sql:332-352` 的專案先例。其他值域 CHECK 可繼續由 app 驗證。

純邏輯放 `crates/schema/src/fengshui/`、建立請求的處理順序、冪等查詢早於 uid 限流、`page_query`、不寫入 F5／F8、無 AI、無自由文字與不做跨使用者統計，這些方向都與現有架構相符。

## Verdict：需重改

整體產品方向可保留，不需要推翻房型問答或先猜後試；但現稿不宜直接進實作。**K01–K04 是 Batch 1／2 的科學誠實閘門，K05–K07 是 Batch 3 的正確性閘門。**修完這七項並補上實際 DB 併發驗證後，才可視為有條件通過。
