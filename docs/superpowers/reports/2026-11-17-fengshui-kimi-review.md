# 風水 v1 + 統一方向 v3 — Kimi K3.1 Pro 對抗式審查(2026-11-17)

審查對象:docs/superpowers/specs/2026-11-17-fengshui-v1-design.md(commit ede24c3)、2026-11-17-talent-direction.md v3。唯讀審查,輸入=兩份文件+repo 規則摘要+風水三審結論。以下為 Kimi 原始輸出(僅去除其內部推理段落)。

• ## 總評

**Verdict：需重改。**

A-only、零 DB、v1 無 AI、不自動帶入 profile gender、年份不 fallback，這些取捨合理；但目前仍有兩個會直接影響結果正確性的 critical：**1900 年立春前會用到未驗證的 1899 命卦**，以及 **uncertain 回應沒有定義如何避免選定單一命卦**。此外，立春時刻精度、版本配對、個資留存與「統一迴圈」的定位都還不足以直接開工。

## A. 命理事實與計算正確性

**F01｜critical｜風水 §2.4、§3、§4、T1/T3：1900 年立春前需要 1899 命卦，超出目前驗證範圍**

公開輸入從 1900-01-01 開始，但 1900 年立春前出生者必須以 **1899 年**算命卦。三審只驗證 1900–2099 的公式等價，T1 也只跑這段；1899 又屬不同世紀，不能直接假設 1900 年世紀公式適用。目前可能越界、套用錯公式，或與 oracle 產生未揭露分歧。

**建議：**保留下拉日期範圍不變，但將內部 `effectiveYear` 明定為 1899–2099，補上 1899 公式、寄卦及獨立 fixture/oracle 驗證。若不支持 1899，就只能把公開下限延後到 1900 立春，不能繼續宣稱支援 1900-01-01。

---

**F02｜major｜風水 §0、§4；統一方向 §4.1：規範所依據的研究檔尚未進 repo，spec 不是可實作的單一事實來源**

公式、mod 9 餘數映射、餘 0、寄卦及大遊年 8×8 表都「不重抄」，但唯一 normative 文件仍在 NUC。多 AI 開工時可能各自補公式，T2 的「oracle **或**研究檔 fixture」也讓驗收標準不固定。

**建議：**把研究四檔收入 repo 作為 Batch 1 的硬前置，並以固定路徑、固定版本引用；附錄至少補上可審查的公式與完整 64 格表。若避免重複維護，可只保留一份 normative 表，但不能以尚未入庫的檔案作為實作依據。

---

**F03｜major｜風水 §3、§6：`HH:MM` 無法安全處理帶秒的立春時刻**

例如立春為 16:26:53，而輸入 16:26。若將它解成 16:26:00，等於替整個 16:26 分鐘猜成立春前；實際出生時間可能在 16:26:53 之後。「立春日無時刻才不猜」沒有涵蓋這種**分鐘精度跨越邊界**的情況。

**建議：**二選一並寫進 API 契約：接受 `HH:MM:SS`；或當輸入分鐘與立春所在分鐘相同時回 `uncertain`。內部測試仍須覆蓋秒級邊界。

---

**F04｜major｜風水 §0、§3、T3：2024 立春樣本互相矛盾，且 JD/UTC 產生流程缺少時間尺度定義**

§0 寫成「2024 立春 **2026-02-04** 16:26:53」，T3 則是 2024-02-04；前者明顯錯誤，不能讓錯字進 golden fixture。另一方面，VSOP2013 計算通常涉及 TT，表卻直接稱「JD(UTC)」；若未定義 TT→UTC 的 ΔT 模型，不同實作可產生不同結果。對天文台抽樣容差一分鐘，也不足以驗證 16:26:53 這種秒級樣本。

**建議：**修正為 2024-02-04；在產生器文件中固定視黃經、of-date 參考架、TT→UTC 與 ΔT 模型，將產生器版本納入 ruleset 版本。除抽樣外，增加獨立來源的逐年或高密度 fixture，不能只驗表長度與單調性。

---

**F05｜major｜風水 §3、§6、§7：UTC+8 限制可作為 v1 取捨，但對非 +8 使用者的輸入語意不足**

只寫「台灣站」不足以防止其他使用者直接輸入出生地當地時間。前端若用瀏覽器本地時區解析 `YYYY-MM-DD`，還可能發生前一日或次日偏移。內部預留 `timezone: Option` 並沒有解決外部契約。

**建議：**明確標示「日期與時間均以 UTC+8 解讀」，並決定非 +8 出生者是否須自行換算；若不支援，應直說限制，而非默默計算。前端以純 civil date/time 處理，不得依賴瀏覽器本地時區；補非 +8 瀏覽器 E2E。

---

**F06｜minor｜風水 §2.2：1/1–2/20 能保守涵蓋分歧，但不是實際分歧帶**

正月初一的一般國曆範圍是 **1/21–2/20**，立春通常為 2/3–2/5。因此 1/1–2/20 的確是所有可能分歧日期的保守超集，**沒有漏掉 1 月下旬的情形**；但 1/1–1/20 屬額外提醒，不應被描述成實際分歧帶。

**建議：**可無需農曆表直接縮成含首尾日的 1/21–2/20；若保留 1/1，改名「冬季保守提醒帶」。文案維持「可能不同」，不可暗示帶內每年、每天必然不同。精確到某年某日才需要正月初一表。

## B. 邊界紅線與 guardrail

**F07｜major｜風水 §1、§7；統一方向 §1：風水 v1 沒有閉合「假說→體驗→誤差→更新」**

v1 只提供八方配置與觀察提示，沒有誤差記錄、回顧或更新步驟；框架表格也在「反思素材」就結束。因此它是自我觀察入口，不是完整迴圈。「實際感受才是你的證據」還可能讓主觀感受被理解成風水效度的證據。

**建議：**明寫「v1 不形成完整測量閉環，感受只用來調整個人空間安排，不用來證明或反證風水」。將上述文案改成「實際感受可作為你調整空間的個人參考」。不要為了文法統一而在 v1 倉促加入日記或測量。

---

**F08｜major｜風水 §2.5、§5：吉星裸名、凶星中性化，本身就會洩漏吉凶**

四星直接顯示生氣、延年等名稱，另外四星改用中性名並常駐「絕命、五鬼」等小註，使用者很容易反推哪些被視為凶。這能降低恐嚇感，但不能宣稱整體呈現已中性；若釋義再變成通用反思句，也可能掏空八星各自的傳統內容。

**建議：**優先讓八星採相同卡片結構與傳統名揭露方式，避免只有凶星被特殊處理。若保留不對稱，應把目標改寫為「降低恐懼措辭，而非隱藏傳統價值判斷」。驗收除了禁詞，還要檢查每星有具體、互不相同且有傳統依據的內容。

---

**F09｜major｜風水 §2、§5、T5/T6：六條紅線不足以涵蓋實際風險，且部分不可直接測試**

最重要的禁科學背書、必然化、醫療／法律／財務斷言只放在語料節；「永不寫入三張表」也沒有涵蓋其他 DB、分析平台或請求日誌。「凶星名永不裸出現」則需正式定義「裸出現」，否則與允許傳統名小註看起來互相矛盾。

**建議：**把內容安全、高風險決策、恐懼式行銷及未同意留存提升為頂層紅線；定義「裸出現＝標題或無語境展示，小註为例外」。每條紅線指定自動測試或人工審查證據，不只寫原則。

---

**F10｜minor｜風水 §2.3、§7、§10.3：公式不預選值得保留，但需解釋，否則只是增加困惑**

不從 profile gender 預選的方向正確；成本是多一次必要選擇，以及使用者可能以為網站在要求性別認同。把 wire 值改成 `mingua-male` 本身不會解決這個問題。

**建議：**保留無預選，在 radio 旁加「這是傳統公式的歷史命名，不代表或推定你的性別；請選擇要使用的算法」。儘早固定 wire enum，不要留給各實作者自行命名。

## C. API／架構

**F11｜critical｜風水 §3、§6、§7：`uncertain: true` 沒有定義主要結果如何處理，可能仍偷偷選一個命卦**

回應同時保留 `mingua`、`directions` 與 `uncertain?`，但沒有說不確定時前兩者是否為 null、是否給兩個候選，或 web 應隱藏什麼。「不猜」目前只是一句意圖，不是可驗收契約。

**建議：**定義 discriminated response，例如 `status: "certain" | "uncertain"`。uncertain 時不得有單一選定的 `mingua/directions`；可要求補時刻，或明確回傳立春前後兩個候選。T4 與 E2E 必須斷言不會顯示單一命卦卡。

---

**F12｜major｜風水 §4、§6、§9：雙版本常數只有回傳，沒有不一致時的 fail-closed 行為**

API 與 CSR web 分別部署，天然會出現新 API／舊 web 的窗口；「背靠背」不能消除它。若 web 語料與 API 回傳的 star id、規則或語料版本不一致，可能顯示錯誤解讀。尤其 API 本身不持有語料內容，`corpusVersion` 的配對責任更需明定。

**建議：**web 編譯時固定 expected ruleset/corpus 版本，回應不符時不顯示結果，只提示重新整理或稍後再試。補 ruleset 與 corpus 分別不一致的測試，並設計部署期間的相容窗口或 feature gate。

---

**F13｜major｜風水 §6：生日與時間放在 GET query，會擴大個資出現在基礎設施日誌的機會**

無狀態不等於必須 GET。出生日期、時間與公式別可能進入 CDN、API、錯誤監控或分析系統的 URL 日誌；僅保證三張 DB 表無資料，不足以支撐整體隱私定位。GET 也較容易被中間層快取。

**建議：**優先評估無狀態 POST JSON，並回 `Cache-Control: no-store`。若堅持 GET，至少明定 no-store、query 日誌遮罩、分析系統排除與錯誤監控去個資；把這些列成部署驗收項。

---

**F14｜major｜風水 §6：400 契約不完整**

`time=24:00`、非法時間、缺 formula、重複參數、空值都沒有定義；現有 `INVALID_DATE` 不適合表示非法時間。也沒有固定錯誤 response shape。

**建議：**補 `INVALID_TIME`，明定缺省／未知 formula 回 `INVALID_FORMULA`，制定 `{ code, message }` 等通用格式與重複參數政策。所有錯誤維持 generic，不回傳 parser、domain 或 DB 細節。

---

**F15｜major｜風水 §5、§6：`schoolNote?`／`disclosures` 可能是文字，破壞「語料不走 API」與雙語設計**

如果 API 回中文說明，web 就無法只靠本地語料切換英文；如果回 id，schema 又沒有寫清楚。`schoolNote` 與 `disclosures` 的責任也重疊。

**建議：**wire 只回穩定 disclosure id 或布林旗標，例如 `schoolDisclosure: true`；所有雙語文字由 web 依 id 呈現。補完整 JSON 範例，包括 UTC 時間格式、nullability、directions 順序與 enum 值。

---

**F16｜minor｜風水 §6：「避免前後端實作漂移」不是計算走 API 的充分理由**

若 web 與 API 都使用同一個 schema crate，本來就是同一實作，不會因為純前端計算而漂移。真正差異是部署版本、額外網路故障與隱私成本。

**建議：**把理由改成「提供其他 client 共用端點、集中更新與部署 probe」等真實收益，並與上述成本一起做 ADR 取捨；不要再以共享 crate 不存在的漂移作為主要論證。

---

**F17｜minor｜風水 §6、§8：verify probe 沒有規定要驗什麼，可能只變成 200 健康檢查**

**建議：**使用固定、非真實個資的測試向量，至少驗證一個完整命卦與八方結果、一個 uncertain 邊界、一個範圍外 400，以及版本欄位存在且符合部署預期；同時斷言無寫入副作用。

## D. 語料

**F18｜major｜風水 §2.5、§5、T5：紅線掃描的語言與語境規則不足**

目前禁詞例子幾乎都是中文，英文可輕易出現 “will”“guaranteed”“research proves”“scientific”等等。另一方面，凶星名本來就允許出現在小註，單純 substring 掃描會誤殺合法小註，或迫使實作者放寬到失去作用。

**建議：**建立雙語禁詞與大小寫、詞形、全半形測試；對「凶星名」採結構化欄位或 DOM 位置掃描，允許指定小註欄、禁止出現在標題與一般內文。加入必須通過與必須攔截的正反 fixture，並掃描所有最終顯示欄位。

---

**F19｜major｜風水 §5、Batch 2：64 件欄位可計數，但尚無內容品質驗收**

「每語約 100 字」不能防止八星內容高度重複、英文只是直譯、提問暗示答案，或凶星被中性化成沒有資訊的通用文案。站長過目也沒有具體檢查表。

**建議：**Batch 2 驗收加入：每星傳統主題明確且彼此可區分、中英由具能力者校訂、提問不預設好壞、無高風險建議、傳統名與來源性質一致。保留站長語義審查，不能以掃描通過代替內容通過。

---

**F20｜minor｜風水 §5.3：反思提問應主動邀請反例，而不是只引導尋找符合經驗**

「在這個方位工作時，專注狀況如何？」本身中性，但若八星都朝各自預期效果提問，仍可能形成確認偏誤。

**建議：**每星至少一題純觀察，並在共用文案鼓勵記錄不符合預期的經驗；不得要求使用者為了「驗證」而反覆嘗試不舒服的配置，也要明說提問不會被上傳或記錄。

## E. 測項

**F21｜major｜風水 §8 T1–T4：現有測項漏掉最危險的時間與日期邊界**

T4 的立春前後一天，測不到真正的秒級判斷；也沒有處理 1900 有效年、非立春日無時刻、分歧提醒帶首尾日及正月初一先於／後於立春的兩種年份。

**建議：**至少加入：

- 1900-01-01、1900 立春前後、2099-12-31 23:59，以及 1899／2100 的 400。
- 立春前一秒、當秒、後一秒；API 的跨邊界同一分鐘。
- 立春日無時刻為 uncertain；**非立春日無時刻不得 uncertain**。
- 1/20、1/21、2/20、2/21 的揭露開關；若保留 1/1 起點則調整斷言。
- 正月初一在立春前與立春後的各一組 fixture。
- 嚴格日期、時間與非 +8 瀏覽器案例。

---

**F22｜major｜風水 T6：「三表零列」不是正確的隔離斷言**

測試環境若已有其他測試資料，不能要求三表絕對為空；只檢查 route 沒有直接 DB handler，也抓不到 transitively 呼叫的寫入。

**建議：**記錄全流程前後 row count，斷言差值為零；另以依賴或型別隔離確保 route 拿不到 DB client。再用靜態審查確認沒有 analytics、日誌或其他平台儲存把輸入送出去。

---

**F23｜major｜風水 §8 Web E2E：缺少部署與客端故障案例**

目前 happy path 無法發現版本配對、儲存損毀或不同語言漏掃。

**建議：**加入舊 web／新 API、corpus/ruleset 各自不一致、API 400、uncertain 不顯單一結果、localStorage 禁用／滿額／損毀／清除、英文 DOM 掃描，以及重新整理後不得讀出已清除資料。

---

**F24｜minor｜風水 T7：同參數逐位一致不是無狀態的完整證明**

伺服器仍可能快取或把不同使用者的資料串錯，而同參數結果依舊一致。

**建議：**保留確定性測試，但另測不同輸入交錯與並行請求、不應共享的個人化狀態，以及快取標頭；不要以 T7 單獨宣稱無狀態與隔離已證明。

## F. 範圍、批次與隱私

**F25｜major｜風水 Batch 0、§9；統一方向 §4.3：RIASEC 下架與風水共用部署窗口，會放大回退爆炸半徑**

兩者沒有功能依賴。若風水 probe 失敗或 RIASEC 410 出問題，可能被迫一起回退，意外恢復已下架功能或撤下正常風水。

**建議：**優先拆成可獨立部署、獨立回退的兩次變更。若必須同窗，至少以獨立 feature gate、各自 verify 與明確回退順序隔離，不以「併本線」作為耦合理由。

---

**F26｜major｜風水 §7、§10.5：預設把生日留在 localStorage，對共享裝置不友善，且保存期限不明**

「比照清除足跡權」不是具體機制；無帳號也不代表生日不是個資。

**建議：**v1 最簡方案是直接不記住生日。若保留，預設不儲存，提供明確 opt-in「在此裝置記住」、一鍵清除、共享裝置提醒與保存期限；儲存失敗不得影響計算。

---

**F27｜minor｜風水 §9、§10：A-only 範圍合理，但五個開放問題不應全部帶進多 AI 開工**

目前最大的風險不是功能太少，而是規約未決導致各批自行解釋。精確雙派計算、完整日記、AI、宅卦都不必為此塞入 v1。

**建議：**開工前至少定案揭露範圍、wire 命名與 localStorage；上北切換可延後，但八方圖必須另有文字列表，避免只能靠羅盤方向理解結果。

## G. 統一方向 v3

**F28｜major｜統一方向 §1、§2；風水 §1：素材層與宣稱層的界線仍需區分「傳統描述」與「經驗效果」**

「這個方位的傳統說法」是可查證的文化描述，不等於「此配置會改善專注」的經驗宣稱。個人觀察也不能自動把素材層升格為可檢驗宣稱。

**建議：**在分層定義中明列三類：傳統來源描述、個人反思提示、可反駁的效果宣稱。素材層只允許前兩類；個人感受可更新自己的安排，不得被寫成已驗證風水理論。

---

**F29｜major｜統一方向 §2：有回饋欄不等於「可檢驗」**

F5 一次性回饋與天賦線自我猜測提供對答案的入口，但若沒有事先固定的宣稱、操作化結果與比較方式，就只能稱為可回饋，不能自然推成有效預測。

**建議：**將「可檢驗」定義為至少具有事前宣稱、明確結果欄位、時間窗、缺失資料處理與誤差呈現；對外更精確地說「提供對答案機制」，不要暗示已證實準確。

---

**F30｜major｜統一方向 §1：三面框架目前偏事後貼標籤，尚未形成設計約束**

風水沒有誤差與更新仍被放進行動面，顯示只要改寫表格文字就能入框；框架因此不能阻止不完整的設計通過。

**建議：**若保留三面框架，要求每個功能 spec 填寫「假說提出者、體驗行動、誤差訊號、更新對象、保存位置、宣稱層級」。缺欄時允許明確標示「非閉環」，而不是硬補迴圈語彙。

---

**F31｜major｜統一方向 §5 風險 14：只靠「審查須過分層檢查」不足以防止升格宣稱**

沒有負責人、檢查表、放行證據，也抓不到隱含因果或英文文案。自動禁詞同樣不能理解語義。

**建議：**將分層檢查設為每批 release gate：列出所有效果句及其層級、雙語掃描、至少一例正確與錯誤文案對照，並由站長或指定 reviewer 簽核。發現升格宣稱時必須退稿，不能只修一個禁詞。

---

**F32｜minor｜統一方向 §2：全站差異化文案可能污染素材層頁面的觀感**

即使只說「本站這些線可檢驗」，若放在共用導覽或風水頁附近，使用者仍可能理解成目前所有功能都可檢驗。

**建議：**文案必須就近指出具體功能，例如「本週預測提供對答案機制」；風水、塔羅、命盤頁不得沿用全站式可檢驗宣稱。

## 最該優先處理的三件事

1. **先封住時間與年份正確性：**補 1899 有效年驗證，修正 2024 立春錯字，定義 TT→UTC／ΔT，並解決 `HH:MM` 跨立春秒數的不確定性；這些未完成前不要進 Batch 1。
2. **把 API 做成可 fail-closed 的契約：**uncertain 不得回單一選定結果，版本不一致不得混顯；同時補齊錯誤格式、雙語 disclosure id、隱私快取策略與對應測試。
3. **修正定位而非擴充功能：**明說風水 v1 不是完整閉環，感受不是風水效度證據；以一致的八星呈現與分層 release gate 防止恐懼文案或「可檢驗」宣稱滲入。
