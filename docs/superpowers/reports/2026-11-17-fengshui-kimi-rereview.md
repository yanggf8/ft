## 2. 修訂新引入的問題

### N01｜major｜風水 §3、T3：固定 ±60 秒不能吸收所宣稱的「分鐘級」未來誤差

文件一方面承認 ΔT 外推可能產生「分鐘級」誤差，另一方面又說由 ±60 秒窗吸收；超過 60 秒的誤差仍可能把出生時間分到錯誤有效年，與「不猜」紅線直接衝突。

**建議：**為每年建立有依據的保守不確定半徑 `r_y`，或提出足以證明 1900–2099 全部誤差均不超過 60 秒的驗證；若做不到，應縮減支持年份或採更寬的保守窗，不得繼續宣稱固定 ±60 秒已吸收所有分鐘級誤差。

### N02｜minor｜風水 §3、§4、T4：重疊規則可理解，但端點與 API 預期值尚未完全固定

`[m,m+60s)` 與 `[L−60s,L+60s]` 混用半開、閉區間本身有數學意義，但 spec 沒有明寫 `m` 是該分鐘起點、比較使用整數 Unix 秒，T4 的「uncertain 開關」也未逐項列出預期結果，實作者仍可能在單點接觸時差一秒。

**建議：**直接凍結判定式：以 `m` 為出生分鐘起點、`L` 為表中立春 Unix 秒，`uncertain ⇔ m ≤ L+60 且 m+60 > L−60`；補 `m=L+60`、`m+60=L−60` 測試。以 2024-02-04 16:26:53 UTC+8 為例，16:25、16:26、16:27 應 uncertain，16:24、16:28 應 certain。

### N03｜major｜風水 §2.4、§6、T1：1899 無法裁定時的退路與兩候選契約不相容

若公開下限只延後到「1900 年立春 instant」，立春當日無時刻及 boundary-minute 輸入仍會要求回傳 1899、1900 兩個命卦候選，但退路的前提正是 1899 命卦尚未通過驗證。

**建議：**若啟用退路，公開下限必須延後到第一個可回 `certain` 的分鐘，並明定所有會產生 1899 候選的輸入如何回 400；不能保留目前的兩候選契約卻只修改一句下限文字。

### N04｜major｜風水 §2.1、§6、T6：POST 與靜態 route 審查不足以保證基礎設施不留存

`no-store` 只約束快取，T6 的「無 analytics/log 呼叫」也抓不到 CDN、反向代理、APM 或錯誤監控自動擷取 POST body，因此「輸入不寫入錯誤監控」目前仍是未驗證的部署宣稱。

**建議：**增加部署驗收項：關閉或遮罩 request body、例外附件與分析事件中的日期／時刻／公式別，並用固定合成 canary 請求檢查正式日誌及監控系統確實看不到這些欄位。

### N05｜major｜統一方向 §1，對照 §2、§6：全站「幫我對答案」文案再次越過素材層界線

「平台每個功能都是這個迴圈的變形」及「使用者只會感覺這個站在幫我對答案」，與風水明定「不對答案、非閉環」及素材層禁止全站可檢驗宣稱互相矛盾。

**建議：**改成「平台依功能提供傳統素材觀察或對答案機制；只有滿足五要件的功能才稱可檢驗」，避免把內部統一理論轉成全站效果暗示。

### N06｜major｜統一方向 §2、§5：五要件已定義，但 release gate 沒有驗證它們

現行 gate 會分類效果句、掃禁詞、附正誤例並由站長簽核，卻不要求對答案層逐項提出五要件證據；因此一份缺少缺失資料處理或誤差呈現的設計仍可能通過 gate。

**建議：**對每個含 (c) 類句子的功能增加五欄放行表：事前宣稱版本、結果欄位與型別、時間窗及時區、缺失資料規則、誤差呈現位置；任一缺欄即只能使用「可回饋」定位，不得以「可檢驗」放行。

## 3. 指定事實與契約核對

3. **定案 1899 驗證或完整退路：**若採退路，必須同時修正公開下限、uncertain candidates 與 400 行為，消除 N03。
4. **把隱私與分層宣稱變成可驗收證據：**補 N04 的基礎設施不留存驗收，並完成 N05、N06 的方向文件修正。
