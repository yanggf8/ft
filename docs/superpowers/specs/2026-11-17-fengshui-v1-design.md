## 0. 三審結論定案(本 spec 的事實地基)

- **v1 = A only**:命卦+個人八方。B(八宅:宅卦配命卦)另立 spec;年紫白備胎不動。
- 事實查證全數通過:命卦分世紀公式 ≡ 四位數字和版 mod 9(1900–2099 代數等價、
  無分歧年份);男命遇 5 寄坤、女命遇 5 寄艮(各派一致);換年界立春為主流,
  《八宅明鏡》原文按農曆年(須並陳揭露);乾命八方合大遊年歌;2024 立春
  2026-02-04 16:26:53(紫金山;新華社 16:27 為進位版)——**實作公式與歌訣以研究檔
  定案文本為準,本 spec 不重抄**;mingli-luoshu crate 為測試 oracle。

## 1. 定位(掛統一框架 v3)

- **行動面、素材層**:八方配置=假說(素材),實際起居感受=體驗;不承諾可檢驗、
  零測量零 DB。文案鼓勵「試著觀察感受」(統一迴圈語彙),但**不下吉凶保證、不借
  腦科學/統計背書**(GUARDRAIL 精神)。
- 隱性 PP:介面不說理論。對外詞彙:「風水·個人八方」。

## 2. 邊界紅線(明文化,實作與審查逐條對照)

1. **風水資料永不寫入 predictions / prediction_feedback / f8_assignments**(route
   檔頭註明;本 v1 為無狀態計算,架構上零 DB 寫入,測試斷言)。
2. **換年派別並陳(揭露式)**:主判定用立春時刻。兩派(立春界 vs 農曆年界)的
   分歧帶=出生日落在**當年立春日與當年正月初一之間**(先後年年不同)——精確
   界定需要農曆正月初一表,v1 不引入(設計取捨),故採**粗揭露**:出生日落在
   國曆 1/1 至 2/20(正月初一可能的最晚日)之間者,一律顯示「傳統另有派別以
   農曆年(正月初一)為界,冬季換年期間出生者兩派年命認定可能不同;本站以立春
   為準」。v1 不做雙版本計算;若站長要求精確並陳再升級(引入農曆表)。
3. **公式選擇明示**:UI 用「男命公式/女命公式」二字明選;**不從 profile 的
   gender 自動預選**(包容不願揭露或不適用二元者)。
4. **年份範圍外回 400**:不 `unwrap_or(fallback_year)`;範圍 1900-01-01 起、
   2099-12-31 止(與立春表覆蓋一致)。
5. **凶星名永不裸出現**:絕命/五鬼/六煞/禍害不作為任何顯示標題;以中性描述呈現,
   常駐小註揭露傳統名與「古籍用語、非吉凶保證」。
6. **v1 無 AI**;日後接 AI 時 GUARDRAIL 逐字適用+語言測試守門(CLAUDE.md 規則)。

## 3. 立春表閉環(前置工程 1)

- `LI_CHUN_JD_1900_2099`:固化常數表,每年一行 JD(UTC)。
- **產生器**:`crates/domain/western` 新 example(`gen_lichun`),以既有
  `sun_apparent_ecliptic`(VSOP2013)離線計算太陽黃經 315° 時刻,`cargo run` 產出表。
- **第三來源交叉驗證**:香港天文台節氣表抽樣對照(產生器輸出 vs 天文台時刻,
  容差 ≤1 分鐘;2024 樣本=16:26:53)。對照紀錄寫進測試 fixture 註解。
- **時區語意**:表存 UTC;輸入以中原標準時(UTC+8)為準(台灣站)換算比較;
  `timezone: Option` 留接口、v1 僅 +8。
- **時刻可選**:無時刻 → 以日期判定(立春日以外無歧義);**恰為立春日且無時刻 →
  回應帶 `uncertain: true` + 揭露「請補出生時刻以精確判定」**,不猜。

## 4. 純邏輯(crates/schema/src/fengshui/)

- `mingua.rs`:年→命卦(公式依研究檔;含寄卦:男 5→坤、女 5→艮);
  輸入=出生時 instant(已過立春判定後的年)+公式別。
- `dayou.rs`:大遊年歌 8×8 對照表(命卦×八方→八星 id);fixture 至少含三審
  查證的乾命八方。
- `lichun.rs`:JD 表+查詢(年份→該年立春 instant UTC;範圍外 Err)。
- `mod.rs`:`FENGSHUI_RULESET_VERSION`(公式+歌訣+判定規則)/
  `FENGSHUI_CORPUS_VERSION`(語料);型別:八卦、八方位、八星 id(吉凶語意只在
  語料層,邏輯層不帶「吉/凶」字串——顯示層的中性化由此保證)。
- **不依賴 domain**(schema 純邏輯規約);mingli-luoshu 僅 dev-dependency 作 oracle。

## 5. 語料(前置工程 2,時程主力)

八星 × 雙語(中/英),每星四件:

1. **中性標題**(顯示用,凶星不裸名):吉星可用傳統名(生氣/延年/天醫/伏位——
   這些詞本身不帶恐嚇語感,可裸用);凶星一律中性重命名+小註。
2. **釋義**(每語 ~100 字):這個方位的傳統說法,語氣=素材非保證。
3. **反思提問**(1–2 題):「行動面」語彙——引導觀察實際感受(例:你在這個方位
   工作時,專注狀況如何?),不預設答案方向。
4. **傳統名小註**:凶星常駐(「傳統稱:絕命位——古籍用語,非吉凶保證」);
   吉星亦註明出處性質。

寫作紅線:禁「必然/一定/保證/招財/剋」級詞;禁科學背書詞(研究/大腦/統計);
傾向可調整(「若感受不合,配置僅供參考」)。掃描測試釘死(比照 interest
`BANNED_WORDS` 模式,本表獨立定義)。

## 6. API(crates/api/src/routes/fengshui.rs)

- `GET /api/fengshui?date=YYYY-MM-DD&formula=male|female[&time=HH:MM]`
  (時刻與日期皆為中原標準時 UTC+8;v1 無時區參數,`timezone: Option` 僅為內部接口)
- 回:`{ mingua, yearBoundary: { rule: "lichun", lichunInstant, schoolNote? },
  directions: [8 × { compass, starId }], corpusVersion, rulesetVersion,
  uncertain?, disclosures: [換年派別粗揭露?] }`。**語料不走 API**:web 為 CSR,
  語料以 schema 常數直接編譯進 web crate,wire 只回計算結果與版本配對。
- 錯誤:`400 INVALID_DATE`(格式/範圍)、`400 INVALID_FORMULA`。
- 無 POST、無 DB、無限流特例(照 chart 類 GET 慣例)。
- 錯誤訊息 generic,不洩內部。
- **為何計算走 API 而非純前端**:schema 純邏輯雖可編譯進 web 直接算,但 API 為
  單一真相源(避免前後端實作漂移的任何可能)、可被 `verify-deployment.sh` probe
  (部署後自動驗證計算正確性)、與 chart 類功能的架構慣例一致。

## 7. Web(crates/web)

- 新頁 `/fengshui`:首頁卡入口(比照塔羅)+profile 卡不入(v1 不綁帳號)。
- 輸入表單:出生日期(必)、時刻(選)、公式別(男命公式/女命公式,radio 明選、
  無預選);年份範圍外前端即擋+後端 400 雙保險。
- 結果:**命卦卡**(卦名+一句中性定位)+**八方圖**(傳統上南下北羅盤式八角;
  圖側註明「上方為南」)+點開方位卡(中性標題、釋義、反思提問、傳統名小註)。
- 揭露帶:換年派別(§2.2 條件)、立春日不確定(§3)、素材層定位一句(「本功能
  為傳統風水的自我觀察素材,非吉凶保證;實際感受才是你的證據」——行動面語彙)。
- `localStorage` 記住上次輸入(無帳號綁定的便利;清除足跡權比照)。
- 文案掃描(§5 紅線)入 E2E。

## 10. 開放問題(自審與 Kimi 審重點)

1. 揭露式並陳(§2.2)夠不夠——站長若要精確雙版本計算需引入農曆表(v1 成本+)。
2. 八方圖「上南下北」對現代使用者的方向感(要不要加慣用上北切換)。
3. `formula=male|female` wire 值命名(避免 gender 語感:`formula=mingua-male`?)
4. 語料釋義的宗教/文化敏感度(風水 vs 迷信觀感)——文案審多一輪站長過目。
5. localStorage 記輸入的隱私慣例(生日的本地留存)。
